DEVELOPMENT RULES

1. Work one step at a time.
Do not make a bunch of random changes at once. Each step should add one clear feature, fix, or system.

2. Keep the game playable after every step.
Every step should be tested before moving on. Do not commit broken code.

3. Test before committing.
After code changes, run the game with F5 and test the feature in-game.

4. Commit only working chunks.
When a feature works, commit it in GitHub Desktop with a clear summary and description.

5. Do not publish yet.
Commits are local only until the project is ready. Do not press Publish Repository unless specifically decided later.

6. Use clear step numbers.
Continue using numbered steps so progress is easy to resume later.

7. Use exact file paths.
When changing code, write the exact file path, such as:
res://Scripts/player_controller.gd

8. Use targeted code instructions when possible.
The user now knows how to search code. Use “find this / replace with this” for small changes. Use full script replacements only for large or risky changes.

9. Do not add useless cosmetic work.
Visual changes should support gameplay, clarity, feedback, or immersion. Avoid wasting time on decoration that does not help the game.

10. Keep important ideas in the documents.
When a major decision, future idea, or system direction is decided, update:
- Decision Log
- Future Ideas
- Game Design
- Technical Notes

11. Preserve working systems.
Do not rewrite major working systems unless there is a clear reason. Build on what already works.

12. When the user says “resume,” continue from the saved resume point.
Current resume point should always be written in Technical Notes.


BACKUP RULES

1. GitHub Desktop is the main backup system.
Every working step should be committed locally.

2. Do not publish yet.
The repository should remain unpublished until the game is ready or the user specifically says to publish.

3. Commit before risky changes.
Before making big changes to player controls, MDT, radio, dispatch, career systems, or scene structure, make sure the current working version is committed.

4. If something breaks, stop and fix it before continuing.
Do not stack more changes on top of a broken version.

5. If a new change breaks the game badly, use GitHub Desktop to compare changes.
Check exactly what files changed before trying to fix it.

6. If needed, discard only the broken uncommitted changes.
Use GitHub Desktop carefully to discard changes only when the last committed version was working.

7. Never delete working scenes/scripts without a backup.
If replacing a system, keep the old working logic committed first.

8. Keep commits small and named clearly.
Good examples:
- Added subject dialogue popups
- Added call cleared popup
- Added laptop MDT career tab
- Added real shift completion progress

9. Do not commit experimental broken code.
Only commit after the user confirms the feature works.

10. End-of-day rule.
Before stopping for the day, commit working progress and update the documents with:
- What was added
- What is in game
- What is in progress
- What is planned next
